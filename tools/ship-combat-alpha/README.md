# Ship Combat Alpha — Under construction

This is a working **movement prototype**, not a complete combat simulator or a verified implementation of Mongoose Traveller 2e rules. Open `index.html` through a static HTTP server. There is no server API, account, storage, campaign import, telemetry, or external runtime dependency.

## Try it

Select one of five sample ships. Side-coloured arrows show velocity and the next coast position, **not facing**. The selected ship's reachable targets are centred on its coast position, so ships with identical thrust and different velocity have different target areas. Click a highlighted hex, or enter axial Q/R coordinates and choose **Plot target**. **Advance round** applies every plot and moves every ship; ships without plots keep coasting. Thrust is not an automatic speed reset or a fixed maximum speed.

Fresh/reset samples use the complete retained catalogue records: Armed Trader (Adventure Class Ships 2023, p.22), Hunting Ship (p.136), Stealth Scout (p.6), repaired Harrier (The Pirates of Drinax, Book 2: The Trojan Reach, Updated, pp.10–11), and Kashu Multirole Fighter (Small Craft Catalogue 2023, p.51). Scenario positions are three times the former sample spacing; velocities, sides and Green crews are illustrative. Missing catalogue fits remain unknown, and current condition follows ordinary preset creation, including the expressly repaired Harrier values. This affects only new/reset samples; explicit imported, custom and saved state is never filled from these defaults.

The four sample ships without exact artwork use explicit **representative** icon overrides: Armed Trader → Free Trader, Hunting Ship → Patrol Corvette/escort, Stealth Scout → Scout, and Kashu → Light Fighter. These are visual stand-ins, not claimed canonical hull matches; automatic catalogue mappings stay unchanged. Harrier retains its existing custom reference-derived silhouette. Saved user icon choices are not replaced.

Edit the selected ship to enter a name, position, velocity and thrust budget. The sample fighter has thrust 9; there is no ceiling of six. Integer budgets from 0 to 10,000 are supported. This is a prototype input bound, not a Traveller rule. Edits clear that ship's plot and leave the camera fixed. Reset or reload starts a fresh sample.

The map is a single proportional axial-hex projection. Pan and zoom never compress separate pair distances. Fit ships frames their actual positions. Range lines join the selected ship to the others; the sidebar lists Euclidean centre distances, kilometres and range bands under the explicit policy below. Hex detail automatically disappears at distant zoom and can also be toggled off. Grid enumeration is bounded to 1,800 cells below 100% map zoom and 3,600 cells at 100% and above; exceptionally large views can still hit that safety cap. The below-100% behavior is unchanged; target legality uses an analytic distance check even when grid detail is hidden. Large thrust never enumerates its millions of reachable targets.

## Workspace and quick placement

The encounter-only ship row sits above the command controls and supports up to ten ships. Each name field contains a Details button. Add Ship is beside the row; Focus Ship centres the selected ship without changing zoom or motion. Saved setup edits refresh the row and selected status immediately; unsaved changes remain drafts.

The oval map retains filled corner station sectors. The top-right Ship Status display is separate from the lower station commands, with independent bounded scrolling on desktop and stacked displays on phones. The map remains available for spatial decisions. Condition and Power/software editors use large rounded popups; Close, Cancel and Escape discard their drafts without committing resources or rerolling. Their original revision and selected-ship guards remain active. Details and encounter setup retain their guarded transactions.

Sensor mode belongs to each ship's setup and defaults to Active. Passive is a manual setup record; neither mode automates detection, electronic warfare or different power consumption. The existing sensor power switch remains separate and can turn the system off. Older states without a mode load as Active while retaining their existing enabled/disabled state and all other records.

**First-stage reinforcement limit:** Add Ship remains accessible during the workflow, but the current engine requires an explicit **Leave workflow and add ship** confirmation before changing membership. Cancel leaves the workflow unchanged. Leaving clears the workflow declaration sequence but keeps ship records, initiative, vectors and resources; after adding ships, manually record their initiative and confirm the workflow again. This does not implement reinforcement rolls, first-action timing, or automatic continuation of an interrupted phase. These rules remain later work.

No new combat resolution, multiplayer, dogfight, camera-relative ship view or campaign storage is introduced. The reviewed mockups guide the shell; their illustrative rule controls are not claims of implemented mechanics.

## Movement profile and limits

The app uses Traveller Companion Update 2024, printed pp.173–175: six-minute rounds, 648 km hex spacing, thrust changing the vector before simultaneous movement, and reverse recorded initiative for acceleration declarations. The continuous range-boundary and deterministic braking policies are documented below. Reaction-engine fuel/performance, mixed six-minute/six-second dogfights, weapons, damage resolution and missiles remain outside scope. Legacy API consumers may retain other manual round durations; guided Companion declarations require six minutes. No source prose, scans or artwork from the books is included.

Positions and velocity components are whole axial coordinates bounded to ±1,000,000; thrust is a nonnegative whole number ≤10,000. Up to ten ships are supported by the engine. Invalid, nonfinite, fractional, oversized, stale or out-of-range commands fail without modifying the supplied state. These safety bounds are prototype limits, not physical rules.

## Engine and command/state API

`engine.mjs` has no browser or I/O dependencies. It owns validation and movement. `geometry.mjs` owns the affine projection and bounded visible-grid calculation. `app.mjs` is an adapter between DOM controls and explicit commands. Capability data (`capabilities.thrust`) is separate from mutable motion (`motion.position`, `velocity`, `impulse`); a separate template snapshot, crew record, situational modifiers and manual condition record accompany each instance.

```js
import {createState, applyCommand} from './engine.mjs';
let state = createState(); // API version 1, five deterministic sample ships
state = applyCommand(state, {
  type: 'plot', shipId: 'merchant', target: {q: -2, r: 2},
  expectedRevision: state.revision
});
state = applyCommand(state, {
  type: 'advance-round', expectedRevision: state.revision
});
```

State is plain JSON: `{version, revision, round, roundMinutes, ships, acceleration}`. `round` counts completed rounds. Each ship is `{id, name, capabilities:{thrust}, motion:{position:{q,r}, velocity:{q,r}, impulse:{q,r}}}`. `createState({ships,roundMinutes})` accepts manual initial values and normalizes them. A successful command returns a new state and increments `revision`; the original object is unchanged.

Commands are `plot` with `shipId,target`; `coast` with `shipId`; `edit-ship` with `shipId,name,thrust,position,velocity`; and `advance-round`. `expectedRevision` is optional for standalone consumers; the UI always sends it. A given initial state and JSON command sequence replay deterministically. This contract can be adapted to another frontend or future server without importing the page.

## Ship selection and crew setup

**Add a ship** adds an independent preset or custom instance; it never replaces the selected ship. The alpha supports ten ships, an approved usability limit rather than a Traveller rule or proven browser ceiling. Initial position and velocity are explicit. Duplicate designs get unique encounter IDs and independent crew, condition and motion. Reset/reload restores the sample. Remove selected ship and Clear all ships require explicit confirmation; cancel leaves the encounter unchanged. Removing a ship preserves every remaining ID, crew, condition and plot. Clearing can leave an empty map, from which all ten slots can be filled with your own ships. Empty encounters cannot advance rounds; clearing ships preserves the round counter. No campaign storage is accessed.

The initial 56 source variants are from **Core Rulebook Update 2022**, **High Guard Update 2022** and **The Pirates of Drinax, Book 2: The Trojan Reach (Updated)**, including small craft and 400-ton ships. Each retains only displacement, printed thrust, hull points, armour when listed and printed-page citations. Book variants remain separate. Missing armour is `null` (not inferred zero). The Express Boat (High Guard, printed p. 158) has no manoeuvre drive: it uses zero thrust and can only coast in this movement prototype; its jump drive does not provide a thrust budget. No hull values are derived from displacement. High Guard's laboratory ship preserves its printed 360-ton hull / 400-ton drive configuration caveat; its Gazelle uses internal tankage without attached drop tanks. The catalogue is not a full ship sheet, rules database or catalogue of every possible module/configuration. No costs, source prose, deck plans or weapon tables are reproduced. The movement conversion follows the named Companion profile above; conditional reaction-drive performance remains a manual limitation.

Custom designs accept displacement greater than zero through 400 tons inclusive, thrust 0–10,000 and optional hull / armour; unknown values remain unknown. Current hull is a manual instance record bounded by known design hull. It does not automatically apply damage, change thrust or resolve combat. Adjusting current thrust in the movement editor leaves the original design facts intact and is labelled as a manual adjustment.

Each ship starts with a quick Green rating: Green **+1**, Regular **+2**, Veteran **+3**, Elite **+4**, Heroic **+5** are TOTAL crew contributions, not skill levels to which a characteristic DM is added. Optional per-role TOTAL overrides replace that rating, including zero. Detailed mode records one named station holder per captain, pilot, astrogator, sensors, engineer, gunner, medic and steward role, including skill/specialty, skill level and characteristic DM. Its displayed crew contribution is skill + characteristic DM; blank holders are unassigned, never silently zero or trained. Switching modes preserves the other mode's saved values. Inactive controls are disabled for validation and are not serialized; applying the active mode keeps the inactive mode's last saved record, discarding any unfinished inactive draft. Switching back before applying preserves the draft controls. These are the user's setup conventions, not a claim that these ratings implement published check rules. Full character sheets are not modelled. Compact crew setup additionally supports independent gunner assignments keyed to weapon mount IDs, including retained assignments for mounts no longer in the design. Situational DMs are separate and are never added to the stored crew contribution. No checks are rolled or resolved.

**Plot stop (uses thrust)** is a convenience for plotting a zero resulting velocity. It costs the full axial magnitude of current velocity, rejects if this exceeds current thrust, and applies only when advancing the round. Faster ships must plot smaller velocity changes over multiple rounds. It does not instantly stop a ship. Thrust zero still coasts.

### Additional command/state contract (version 1, additive fields)

Normalized ships now include `template` (nullable design snapshot and source), `crew:{mode,rating,overrides,details}`, `condition:{hull}` and `situational` (per-role DMs), separately from capabilities/motion. Legacy initial ship inputs receive synthetic/unknown design defaults and Green crew. Unknown/private fields are discarded.

- `add-ship`: `presetId` or custom `template`, instance `name`, initial `position` and `velocity`. Successful commands assign the first available `ship-N` ID. Adds reject at ten without mutation.
- `set-crew`: `shipId`, complete `crew` and separate `situational` records.
- `set-condition`: `shipId`, `condition:{hull}` (`null` means unknown).
- `brake`: `shipId`; plots a stop only when the velocity-change budget permits it.
- `remove-ship`: `shipId`; removes that instance only.
- `clear-ships`: clears all ships while retaining encounter timing. The frontend confirms both removal commands before sending them; engine callers must supply their own user confirmation policy. Empty ship arrays are valid, with a neutral fit camera.

All existing expected-revision and atomic rejection guarantees still apply. Templates and crew do not supply implicit movement bonuses. Pure `setup.mjs` validates these records; `catalogue.mjs` contains the cited minimum design facts. No server, storage or external runtime dependency was added.

## Encounter Setup and ship-computer console

**Encounter Setup** opens a large desktop dialog or full-screen phone editor. Base records, adding/removing ships, crew and appearance live there rather than filling the movement sidebar. The sidebar retains ship selection, movement and compact reference; each instance name has a smaller muted class/subtype beneath it. The persistent computer panel under the map shows selected-ship Hull, Power and Fuel gauges with numeric labels, Crew/Cargo/Life Support and manually recorded criticals. Unknown values remain explicitly unknown, distinct from recorded zero; mockup examples are not defaults.

Setup uses an isolated draft. All loaded-ship fields are collected and validated on **Save encounter**, which commits one guarded revision. Selecting another draft ship retains valid edits within the draft; **Cancel** or Escape discards the entire draft without rollback writes to live state. Removing/clearing ships requires explicit confirmation and affects the draft until Save. A stale draft cannot overwrite a changed live revision. Native dialogs provide keyboard focus containment and restore focus after closing; phone controls remain full width with a persistent Save/Cancel footer.

**Place on map** temporarily closes the dialog while keeping its draft. It shows a distinct placement preview over the proportional map. Dragging pans without placing; clicking/tapping a hex chooses a preview and updates the coordinate reference. **Use this position** returns the Q/R values to setup; **Add to draft** and **Save encounter** are still required. Cancel placement returns with the original input coordinates, and Cancel setup discards any draft additions. Ordinary map clicks retain movement/selection behaviour. Manual Q/R entry remains the keyboard fallback. No placement changes velocity or immediately adds a live ship.

### Complete optional records, manual condition and overrides

Custom entry accepts design/class, displacement (at most 400 tons), TL, hull/armour/thrust, rated plant output, mode-dependent system power requirements, fuel and cargo capacities, crew complement, jump rating, sensors, computer/software and named weapon mounts with types/counts/initial ammunition. Blank optional fields are unknown. Explicitly empty equipment lists differ from unknown equipment. Equipment validation bounds are prototype safety limits, not assertions about legal Traveller construction. Existing Core/High Guard presets retain their verified minimum hull/movement facts; untranscribed equipment is unknown rather than silently zero or inferred.

**Every ship can be manually adjusted.** The original `template` and source are preserved; `designOverrides` holds only changed fields for that instance. The editor marks overridden fields and shows the original template, and the console lists active override paths. Clearing an override to its original value removes that override. Custom designs retain their original entered template in the same way. Synthetic samples can optionally be given manual base facts. Editing design facts does not automatically repair hull, refill fuel/ammunition, change current power output or apply critical effects. Current thrust is separately editable; the API changes it to design thrust only when explicitly requested. Reducing a known capacity below its current recorded amount rejects rather than clamping the condition; adjust the manual condition first.

The separate **Edit condition** dialog records current hull, fractional fuel/cargo tons, crew available, life-support status, current plant output and used power, current ammunition/status and structured critical records (system, severity, recorded effect, manual status). Save validates nonnegative values and known capacity bounds; Cancel leaves state unchanged. Active/resolved critical records do not automatically alter any ship capability. Orphan weapon-condition records are retained and labelled if a base mount is removed, rather than silently deleted.

Power terms are deliberately separate: **rated plant output** is a base fact; **current output** and **used Power** are manual condition records. Remaining Power is current output minus used Power only when both are known; a negative value is shown as a deficit. Requirements are reference data, never blindly summed across mutually exclusive modes. Fuel capacity and current fuel are tons; they are not a reaction-engine thrust reserve. No fuel burn/leak, ammunition use, damage, repair, life-support or crew-loss simulation is performed by advancing a movement round.

Generic crew has one ship-wide total bonus by default (Green +1, Veteran +2, Elite +3) and an optional editable general total. **Adjust individual roles** provides optional total overrides; a visible indicator lists active overrides even when the disclosure is closed. Detailed mode records assigned stations with optional names, explicit skill/specialty, skill level and characteristic DM. Unassigned is not skill zero. Inactive-mode controls do not participate in validation/serialization; saved values of the other mode are preserved. Crew stays separate from hull templates and situational modifiers remain separate.

### Companion Update 2024 movement profile
Source: **Traveller Companion Update 2024**, printed pp.173–175 (Mongoose Publishing). The bounded movement profile uses six-minute rounds and 648 km centre spacing. Axial Q/R coordinates are the application's hex basis, not the book's diagram-axis labels. Inertia persists; thrust changes the vector before simultaneous movement. No facing, initiative rolling, attacks, missile/dogfight/flyby resolution, combined reaction-drive model or larger-timescale abstraction is introduced.

Guided acceleration declarations require a manually recorded initiative for every ship. Lower initiative declares first; equal values use a referee-editable tie order and then stable ship ID. Initiative is retained until manually changed, never rerolled by round. Only the next ship can change its plan/reservations while declarations are active. Confirmation records the chosen vector change without moving the token. Every ship must declare before simultaneous resolution. Cancel declarations reopens the existing plots without moving anything. Direct manual plotting/Advance remains explicitly available outside guided declarations for legacy/freeform use.

`flight` is an additive per-instance record: optional `initiative` (unknown by default), integer `tie`, reserved `evasion` and `gunners` thrust, and boolean `braking`. Movement budget is current thrust minus the two reservations; reservations cannot exceed thrust. Reservations carry forward until edited (UI policy), with no automatic evasion/gunnery rolls. Increasing reservations that conflict with a manual plot rejects atomically rather than silently rewriting it. Continuing braking recomputes its preview from the current budget. `record-initiatives`, `set-flight-plan`, `begin-acceleration`, `declare-acceleration`, and `cancel-acceleration` are validated, revision-guarded commands. `acceleration` is null outside the guided sequence, otherwise its immutable ordered IDs and declared prefix are validated. Old version-1 records without these fields normalize to unknown initiative, zero reservations and no stop intent. No storage adapter or campaign migration writes are added.

`brake` now sets a continuing stop intent. Each `advance-round` applies at most one round's legal reduction, moves once with the reduced vector, and recomputes the next preview. Reaching zero clears the intent; zero available thrust coasts with intent retained. Manual Plot or Coast cancels it. Integer cube rounding chooses a deterministic shortest digital straight-line reduction; this choice is an implementation policy, not a claim that the source specifies a unique autopilot path. No budget overshoot, vector reversal, skipped rounds, instantaneous stop, fuel use or damage resolution occurs.

Physical range uses Euclidean centre distance `sqrt(dq²+dq*dr+dr²) * 648 km`, independently of hex-step thrust cost. The continuous-boundary implementation policy compares spaces directly to maxima 1/15/38/77, equivalent to outward rounding for the printed table; same hex is Adjacent/Close, >1 is Medium, >77 Distant. The optional two-space Short extension is disabled. Floating-point tolerance is numerical only; formatted display rounding never changes the band. Camera zoom never changes physical scale or time.

Optional versioned `workflow` state records the phase and confirmed initiative snapshot. Legacy states without it remain in manual mode. ### Gunnery declarations

The existing Attack phase has Declare and Resolve substeps. Eligible ships (those with turret records) commit lowest to highest initiative under the labelled home rule. Each turret has Previous/Next navigation, an installed-weapon dropdown supporting four recorded slots, and one exclusive attack, laser point-defense, sand or Hold choice. Core 2022 pp.168/171 restrictions are retained; no permissive High Guard mixed-use mode is enabled. Known shared gunner assignments cannot allocate the same person to multiple turret uses.

Only beam/pulse lasers, missile racks and sandcasters are supported in this bounded declaration stage. Unsupported types, non-turret mounts and unverified mount quantities are not inferred into extra attacks. Legacy type labels are recognized only when they match those supported weapons; unknown fits remain Hold-only. Detailed crews need a recorded gunner; simplified crews use their existing generic station model. Condition records marked offline/destroyed cannot commit active turret use.

Choices remain local drafts until explicit Commit Declarations. Cancel discards only that draft. Committed ship declarations are normalized in the existing versioned workflow and survive JSON save/load; earlier ships cannot revise them. Leaving a partially committed declaration sequence is blocked. Once all declarations are committed, explicit direct-fire resolution unlocks; remaining unsupported attacks require a separate GM acknowledgement. New rounds start fresh declarations and preserve Pilot thrust reservations. Older saves without declaration records still load, including legacy Crew Actions snapshots.

Declarations are intent, not resolution: no dice, ammunition, Power, damage, missile movement or defenses are applied. Range, ammunition, Power and reaction eligibility remain resolution checks. A target destroyed later retains its original target record and holds fire without retargeting at resolution. Manual critical history is unchanged.


### Direct-fire resolution

After locked declarations, **Resolve direct fire** applies eligible beam/pulse laser attacks highest initiative first in one revision-guarded transaction. Core 2022 pp.166–171 supplies Aid Gunners, range/weapon/target modifiers, linked weapons, armour, sand and critical calculations; High Guard 2022 Advanced Fire Control uses its recorded running rating. Simplified crew rating supplies skill, while detailed crew needs applicable recorded skills. Unknown operating Power, disabled weapon loads, unknown required inputs, modified weapons, damaged/manual systems and unsupported cases remain visibly manual. Fire Control shared allocation, multiple defending sand turrets and adjacent/close dogfighting are not inferred.

Defenses use committed choices only. The approved policy ranks attacks by maximum listed weapon damage plus linked bonus before dice, then initiative/turret order for ties; execution still follows initiative. Evasion uses one reserved thrust per allocated attack and the Pilot skill penalty. Aid Gunners consumes one reserved thrust once for that ship’s attacks. Usage is recorded separately from next-round reservation preferences. Sand uses one canister per reaction, a successful check adds 1D + Effect protection and linked casters add +1 each. **One defensive use per sand turret per round is a home rule**, with no slider. Allocations are not reassigned with hindsight after an attack becomes Hold.

Damage updates current Hull and Armour. Attack and sustained-damage criticals record separate hit history with one current severity per system: max(incoming, previous + 1), capped at 6; another hit at severity 6 adds 6D hull damage. The approved interpretation applies only the resulting severity’s effect, retaining persistent prior damage without replaying skipped levels. Hull damage and basic Armour loss are automated. Other system effects, including secondary severity changes, remain explicitly marked for GM handling; a required GM note acknowledges handling without repairing or resetting recorded severity. Pending critical effects block automated movement and the next round until explicitly acknowledged, including after leaving/restarting workflow. Existing manual critical records are preserved.

Committed results retain inputs, dice, defense allocations and usage. Back/Next, Close, reopening and JSON save/load never reroll or reapply damage. Optional `combatHistory` archives replay-validated snapshots (up to 100 round records); `combatDamage` retains per-ship severity/history. Legacy saves omit these fields safely. Manual-only rounds retain their declarations and GM acknowledgement in the same archive. Missile attacks require explicit manual acknowledgement; point-defense reservations remain recorded but are not automatically executed. This stage does not launch missiles or resolve impacts. End Round does not silently resolve them.

Earlier movement/setup sections describe their original bounded stages; this section supersedes their statements that firing and initiative integration are unavailable. No campaign storage adapter, repair system, reinforcement insertion or multiplayer is added.

### Standard missile workflow

Locked declarations now launch verified **Standard** missiles in the same highest-initiative-first transaction as direct fire. Each installed selected rack launches one missile, capped by known loaded stock; one ship/target/type/round forms one salvo. Unknown ammunition, unsupported missile types, modified fits and unverified Power stay visibly manual. Ammunition is spent once on launch. Launcher TL and Launch Solution are captured at launch; an autonomous salvo survives destruction of its launcher. A destroyed target is not replaced.

**Companion Update 2024 pp.175–176 replaces the Core flight-time table.** Salvos begin at the launcher with scalar speed equal to the nearest whole Euclidean magnitude of its velocity. They neither accelerate nor move in the launch round. Each subsequent Manoeuvre adds Thrust 10, decrements the ten-round endurance, and moves toward the target after all ships move. Arrival on the tenth move is allowed before a non-arriving salvo becomes inert. Continuous axial coordinates preserve the exact Euclidean travel allowance; this deterministic straight-line pursuit and ships-first scheduling are implementation choices. Impacts occur last in Attack under the approved ordering rule. This bounded Core/Companion profile does not enable High Guard's optional five-round salvo attrition or variant missile rules.

Core 2022 pp.172–173 supplies launch detection and optional start-round scans. Current ship-contact knowledge is not recorded, so automatic launch detection conservatively uses the unrecorded-launcher 8+ case, with the published salvo-size bonus. Known-launcher 6+ is supported by the arithmetic but is not inferred from the GM seeing a ship token. Scans explicitly roll once per observer at the beginning of the round, before any plot commitment. The map and missile popup show only that selected ship's own or detected active salvos. The encounter remains a referee view; this is not multiplayer secrecy or a player-export security boundary. Active/passive setup values remain intact; no invented passive modifier is added.

**Electronic warfare stays in Crew Actions**, not immediately before impact. Core p.173: 10+ Electronics (sensors), removing Effect missiles; one attempt per salvo per round. This interface permits one EW action per ship's sensor operator per round. Military/Improved/Advanced jammer hardware, working sensors and known operating Power are required. The optional civilian/basic override remains deferred and off; no arbitrary penalty is invented. Core p.181/HG p.21 sensor-suite DMs and HG p.74 running Electronic Warfare ratings apply. Special countermeasure suites are explicitly manual. Protecting another ship is limited to the same map hex, a conservative Close-range eligibility approximation until sub-hex positions exist.

Committed laser PD uses Core p.171: Gunner (turret) against 8+, removing Effect missiles. Same-type linked lasers add count minus one (HG p.81 extends to quad); ordinary beam/pulse attack bonuses do not apply. A turret is used at most once, and existing declaration rules prevent attack/defense double use and duplicate named gunner allocation. Defenses prioritize maximum listed damage before attack dice, then initiative/tie order. If a PD turret destroys its assigned salvo, remaining unused turrets may transfer to the next highest-priority **unresolved** salvo; already resolved attacks are never revisited. Evasion shares the recorded allocation budget with direct fire and requires detection. Sand is not missile PD.

Core pp.79,172–173 and HG pp.36,74 provide Standard TL7/Thrust10/4D/Smart, launch TL/software, salvo-count attack DM and impact damage. Gunner skill and range DM do not enter missile attacks; the Distant-launch penalty and loss of Smart for Adjacent/Close launches remain. Armour is deducted from one 4D roll, then multiplied by the lesser of Effect and remaining missile count; Effect zero causes no damage. Existing Hull/Armour critical automation and manual-system gates apply. Pending manual missile impacts require an explicit GM note and become permanently spent, preventing later automatic reapplication.

Optional `missileCombat` stores salvos, detections, scans, EW and replay-validated impact inputs/dice/results. Old saves and old direct-fire archives remain valid. Launch, movement, scans, EW, PD and impacts are revision/round guarded; reopening and results navigation never roll. A maximum of 1,000 archived salvos and bounded event records protects import/runtime; export the encounter before reaching the limits. No campaign storage is read or written. Remaining crew actions, reinforcements, dogfighting and broad navigation cleanup are separate stages.


### Crew-action workflow

Building on the standard missile workflow, Actions provides a station action popup with explicit manual adjudication, a GM skill/difficulty roll, saved results, Change Position, and a Captain damage overview. Sensors can change Active/Passive mode without spending an action and opens the existing missile scan/EW flow; EW and other sensor actions share the same operator allowance.

Core 2022 pp.171–172 informs temporary Repair System: 8+ Engineer, minus current severity, +1 for each consecutive round of work on the same latest critical. A new hit resets effort. Success records 1D hours. The GM must apply eligible temporary effects and review their expiry; Hull, destroyed equipment, severity and critical history are never silently restored. Expired repair reviews gate further automated movement. Generic declared rolls record results only; Leadership, Astrogation, general sensor locks, communications, boarding and other effect application remain manual.

The destination's previous operator stands down; simultaneous swaps are supported. Pending moves cannot be bypassed by leaving the workflow and editing crew. Legacy saved firing snapshots without the new duty ledger retain their original calculation. Source role and roll modifiers are retained in new results. No campaign storage is read or written.
